## 1. 目的・対象業務

資格試験の問題集を解きながら、1問ずつ回答を記録し、自己採点して学習状況を振り返る。
元のシステムは「基本情報技術者試験 科目B」専用だったが、**さまざまな資格試験に使える汎用的な仕組み**として作り直した。

## 2. 決定事項（元のシステムからの変更点と理由）

| # | 決定事項 | 理由・経緯 |
|---|---|---|
| D-1 | **試験マスタを追加**。ユーザーごとに試験（例：基本情報 科目B、簿記2級）を登録し、カテゴリ・学習・集計・問題一覧はすべて試験ごとに分ける | 利用者の指示「汎用的な仕組みにする」。試験の区別なしにする案と比べ、試験マスタ方式を利用者が選んだ |
| D-2 | **回答は自由記述**（1〜255文字、改行可）。改行コードは LF にそろえて保存。空白だけの回答は不可 | 利用者の指示「自由記述を前提とし255文字等に対応。改行も含められるとなおよし」。元のシステムはひらがな1文字だけだった |
| D-3 | 試験を作ると「未分類」カテゴリを自動で作る | 回答の記録にはカテゴリが必須のため、登録直後から学習を始められるようにする。元の初期カテゴリ（アルゴリズムなど5つ）は科目B専用なので使わない |
| D-4 | 同時に進められる学習は**ユーザーごとに1つ**（試験をまたいでも1つ） | 元の業務ルール「同時に進行できる学習は1つだけ」を維持 |
| D-5 | ログファイルは `SystemRunningLog.log`。約2MB（設定で変更可）を超えたら `SystemRunningLog1.log` に切り替え、1世代だけ残す。時刻は日本時間 | プロジェクトの開発方針と、利用者の指示「ローテーション後は SystemRunningLog1.log」 |
| D-6 | ユーザーごとの DB ファイル分割（`practice.sqlite3.user-<ID>.sqlite3`）をやめ、**1つの DB にまとめて** `user_id` で分ける | ファイルが増え続けると保守・バックアップ・PostgreSQL への移行が難しくなるため。データの独立性は、すべての SQL でログイン中のユーザーに絞り込むことで保証する（結合テストで確認済み） |
| D-7 | 日時の保存形式は元の仕様どおり（学習は日本時間、回答は UTC で保存し表示時に +9 時間） | 旧データの取り込みで変換を不要にするため |
| D-8 | 旧 DB の取り込みはサーバーの起動時ではなく、**別の取り込みツール**（`import_legacy`）で行う | 新 DB は構造が異なり、取り込み先のユーザー・試験を指定する必要があるため |
| D-9 | **インターネットに公開し、HTTPS で運用する**。暗号化は nginx が受け持ち、証明書は Let's Encrypt（Windows は win-acme、Ubuntu は certbot で自動更新）。API サーバーは 127.0.0.1 だけで待ち受ける。nginx でもログイン系 API の回数を制限する（接続元 IP ごとに 1 分 10 回） | 利用者の指示「インターネットに公開」。アプリ側はすでに HTTPS 前提の設定（Secure Cookie・プロキシ経由の接続元 IP）を持っていたため、プログラムの修正は不要 |
| D-10 | **API サーバーは Windows サービスとして常時起動する**。exe 自身が `install` / `uninstall` を持ち、自動起動・異常終了時の自動再起動（10 秒後、3 回まで）を設定する。サービスは LocalService アカウントで動かし、書き込み権限は data / logs だけに与える。サービスとして動くときはホームフォルダ（既定は exe のフォルダ）を作業フォルダにする。C ランタイムを exe に静的に取り込み、Visual C++ 再頒布可能パッケージを不要にする。画面は exe に組み込まず nginx で配信する | 利用者の指示「exe をサービス化して常時起動させる」「画面は入れる予定ではない」。サービスは作業フォルダが System32 になるため、置き場所を固定しないと設定・データ・ログが別の場所に作られてしまう。インターネット公開のため、最小権限のアカウントで動かす |
| D-11 | **配置に使うものを `deploy/` にまとめ、使う場所ごとにフォルダを分ける**（`windows-service/`：API サーバーのサービス登録・更新・解除、`nginx/`：nginx の設定と配置、`ubuntu/`：将来の移行用）。`deploy/build-release.ps1` が同じ分け方の `release` フォルダを作り、サーバー PC ではスクリプトを実行するだけで配置できるようにする。nginx の設定は http 版・HTTPS 版のどちらも `conf\study-record.conf` という同じ名前でコピーする。nginx（Windows 版はサービス登録の機能を持たない）はタスク スケジューラで Windows の起動時に LocalService で起動する。配置スクリプトの実行記録も `SystemRunningLog.log` に残す | 利用者の指示「実装方法がわかりにくい」「Windows のサービスとして動かす」「nginx で使うものはそれでわかるように」。手順が README に開発・Windows・Ubuntu・nginx と混在し、nginx の設定がプロジェクトのフォルダを直接参照していたため。設定ファイルの名前をそろえることで、http 版と HTTPS 版を両方読み込んで nginx が起動しなくなる誤りを防ぐ。nginx をサービス化する外部ツール（WinSW・NSSM）は追加のダウンロードが必要なため使わない |
| D-12 | **毎日開きたくなる学習計画の機能を追加する**：忘却曲線にもとづく復習日（間隔反復）、試験日までの残り日数と 1 日の目標、連続学習日数、学習カレンダー、苦手なカテゴリ。習熟度は「最新から数えて連続で正解した回数」（0〜5）とし、次の復習までの日数は 1→3→7→14→30→60 日。一度でも間違えると 0 に戻る。習熟度と復習日は保存せず、正誤の履歴から毎回計算する。連続学習日数は、今日まだ解いていなくても昨日まで続いていれば途切れていない扱いにする | 利用者の指示「お金を払ってでも使いたいレベルにする」。記録するだけでなく「今日なにを解けばよいか」を示すことで学習の継続と定着を助ける。計算結果を保存しないため、回答の修正・カテゴリ変更・旧データの取り込みをしても矛盾が起きず、DB の変更は試験日・目標の 2 列だけで済む。間隔はライトナー方式の一般的な値を採用し、`domain/study_plan.rs` の定数で変えられる |
| D-13 | **示すだけでなく、すぐ解ける・最後まで続けられるようにする**：今日の復習を 1 回の学習で順番に解く「まとめて復習」（問題名称・問題数・カテゴリを 1 問ずつ自動で入れる。最大 30 問、手元に無い問題はとばせる）、合格準備度（習熟度の平均。全問習得で 100%）と試験日までに必要なペース、見直しノート、問題ごとの平均回答時間と並べ替え。必要なペースは「全問を習得するのに足りない正解の回数 ÷ 試験までの日数」の目安とする | 利用者の指示「もう少し考えてみてください」。D-12 は「何を解くか」を示すところまでで、解き始めるまでの手間（問題ごとに名称・番号・カテゴリを入力し直す）が残っていた。問題集の本文はアプリに無いため、問題の特定に必要な情報だけを並べる方式にした。復習リストは学習 ID と組にしてタブ内に保存し、記録済みかどうかは回答の問題名称＋問題数で判定するため、画面を開き直しても続きから再開できる（とばした問題はその画面を開いている間だけ覚える）。準備度・ペースは保存せず毎回計算する（D-12 と同じ理由） |
| D-14 | **有料で使ってもらえる製品にするため、「知ってもらう → 使い始める → 続ける」の入口を作る**：ログイン前のトップに紹介ページ（`/welcome`）、試験が無い利用者には「はじめての設定」（`/setup`。主要 10 試験のテンプレートから選ぶと出題分野のカテゴリがそろう → 試験日・1 日の目標 → ダッシュボード）、まだ 1 問も解いていない間は「最初の学習を始める」を表示。継続のために、準備度の推移（8 週）、実績バッジ、ホーム画面に追加できる PWA（マニフェスト・アイコン・サービスワーカー）を追加した。紹介ページには利用者の声や利用者数など裏付けの無い数値は載せず、画面の見本は「表示例」と明記する。料金・決済は作っていない | 利用者の指示「有料ユーザーをたくさん獲得できそうな最強の study-record」。登録しても試験・カテゴリを自分で作るまで何もできず、そこで離れやすかった。料金・決済サービス・特定商取引法の表記は事業としての判断と法的な責任を伴うため、実装せず課題に残した。テンプレートのカテゴリは各試験の公式の出題範囲の大きな区分にそろえ、作成済みの試験には影響しない。サービスワーカーは個人の学習データを端末に残さないよう API をキャッシュしない。準備度の推移は保存せず、各週の終わりまでの回答から習熟度を求め直す（D-12 と同じ理由） |
| D-15 | **検索エンジン対策（SEO）**：紹介ページだけをビルド時に HTML として書き出す（`frontend/scripts/prerender.mjs` → `dist/welcome/index.html`。本文・タイトル・説明・正規の URL・OGP・Twitter カード・構造化データ WebApplication / FAQPage）。nginx はログインの Cookie が無い人のトップ（`/`）にこの HTML を返し、ある人にはアプリを返す（`Vary: Cookie`）。紹介ページ以外は `noindex`。`robots.txt`（`/api/` は巡回させない）・`sitemap.xml`・SNS 共有用の画像（1200×630）を用意し、文字のファイルは gzip で圧縮する。画面ごとにタブのタイトルを「見出し \| 学習記録」にする。公開するドメインはビルド時は仮のもので、`install-nginx.ps1 -ServerName` が書き換える | 利用者からの質問「SEO はどうですか」。画面を JavaScript で描くため、検索エンジンや SNS が最初に受け取る HTML が空で、トップも JS で別の URL へ移すだけだった。サーバー側で毎回描く方式（SSR）はサーバーの構成が大きく変わるため、検索に出す必要があるのが紹介ページだけであることから、ビルド時の書き出しにした。試験名はビルド時に API を使えないため、バックエンドのテンプレートの定義から読み取り、画面とずれないようにする。よくある質問の構造化データは画面と同じデータから作る |

## 3. 機能一覧

### 3.1 元の機能（F-01〜F-31）

`機能一覧.md` の F-01〜F-31 をすべて実装した。業務ルールとエラーメッセージは元の資料のとおり。
ただし次の点は D-1〜D-8 に合わせて変えている。

- F-02 回答：全角ひらがな1文字 → 自由記述（D-2）
- F-08〜F-21：試験ごと（D-1）
- 初期カテゴリ：「未分類」だけ（D-3）
- F-28 起動時の復旧：全ユーザー分をまとめて処理する（D-6）
- F-29 データ移行：取り込みツールで行う（D-8）
- F-31 運用ログ：ファイル名と世代の付け方（D-5）。サービスとしての起動に失敗したときのエラーも、別ファイル（旧 `service.log`）ではなく `SystemRunningLog.log` に記録する（D-10）

### 3.2 追加した機能

| # | 機能 | 内容 |
|---|---|---|
| A-01 | 試験マスタ | 試験の登録・名称変更・削除（学習記録がある試験は削除できない） |

| A-09 | カテゴリの並び替え | カテゴリ画面で上下に並べ替えられる |

| A-11 | キーボード操作 | 回答欄で Ctrl+Enter を押すと記録する（Enter だけなら改行） |
| A-12 | 今日の復習（間隔反復） | 問題ごとに習熟度（0〜5）と次の復習日を計算し、復習日が来た問題を「復習を過ぎた日数が長い順」に表示する。元の復習一覧（最新が不正解）はタブで切り替えて表示できる |
| A-13 | 学習目標 | 試験ごとに試験日と 1 日の目標問題数を設定できる。ダッシュボードに試験までの残り日数と今日の達成度を表示する |
| A-14 | 今日やること | ダッシュボードの先頭に、試験までの日数・今日の目標・連続学習日数（最長記録）・今日の復習の件数・習得済みの問題数をまとめて表示する |
| A-15 | 学習カレンダー | 過去 26 週の日別の解答数を色の濃さで表示する。目標がある場合は目標を達成した日が最も濃くなる |
| A-16 | 苦手なカテゴリ | 3 問以上解いていて正答率が 80% 未満のカテゴリを、正答率が低い順に 3 件まで表示する |
| A-17 | 解き直す | 問題一覧・復習から、問題名称・問題数・カテゴリを入れた状態で学習を始められる |
| A-18 | まとめて復習 | 復習画面の「まとめて復習する」で、今日の復習の問題（表示している順に最大 30 問）を 1 回の学習で解く。回答画面に進み具合と今の問題を表示し、記録するたびに次の問題を入れる。「この問題をとばす」で次に進める |
| A-19 | 合格準備度とペース | ダッシュボードに準備度（全体・カテゴリ別）、習得までに必要な正解の回数、試験日までに必要な 1 日の問題数、直近 14 日の平均を表示し、ペースが足りているかを伝える |
| A-20 | 見直しノート | 採点時に残した正解・メモを新しい順に一覧表示する。キーワード（スペース区切りで AND）・カテゴリ・不正解のみで絞り込める |
| A-21 | 平均回答時間と並べ替え | 問題一覧・復習に問題ごとの平均回答時間を表示し、正答率が低い順・平均時間が長い順・習熟度が低い順に並べ替えられる |
| A-22 | 紹介ページ | ログイン前にトップを開くと表示する。機能・使い方・テンプレートがある試験・よくある質問と、新規登録への案内 |
| A-23 | はじめての設定と試験のテンプレート | 試験が無い利用者をトップから案内する（試験の管理の「テンプレートから追加」からも開ける）。テンプレート（IT パスポート、基本情報 科目A・B、応用情報 午前・午後、簿記 2 級・3 級、FP 2 級、宅建、TOEIC L&R）を選ぶと出題分野のカテゴリを作る。試験日・1 日の目標もここで設定できる |
| A-24 | 準備度の推移 | 合格準備度を 1 週おきに 8 週分さかのぼって折れ線で表示し、最初からの伸びをポイントで示す |
| A-25 | 実績バッジ | 累計の解答数・最長の連続学習日数・習得済みの問題数・準備度・目標を達成した日数で 14 種類（目標が未設定なら 12 種類）。次に達成できそうな実績と残りを表示する |
| A-26 | ホーム画面に追加（PWA） | マニフェスト・アイコン・サービスワーカーを用意し、スマートフォンのホーム画面からアプリのように起動できる。画面は通信できないときも表示でき、API は常にサーバーへ問い合わせる |
| A-27 | 検索エンジン対策 | 紹介ページの HTML の書き出し、正規の URL、OGP・SNS 共有用の画像、構造化データ（WebApplication・FAQPage）、robots.txt・sitemap.xml、ログイン後の画面の noindex、画面ごとのタイトル、gzip 圧縮 |

## 5. API

すべて JSON。エラー時は `{ "error": "メッセージ" }`
（400 入力エラー / 401 未ログイン / 403 不正な要求 / 404 データなし / 409 状態の矛盾 / 429 試行回数超過 / 503 メール未設定）。

## 6. データモデル（SQLite）

スキーマは `backend/src/infrastructure/database.rs` の `MIGRATIONS` に定義し、`PRAGMA user_version` で版を管理する。

| テーブル | 主な列 | 備考 |
|---|---|---|
| users | id, name, email（大文字小文字を区別せず一意）, password_hash | パスワードは Argon2id |
| sessions | token_hash, user_id, csrf_token, expires_at | トークンは SHA-256 のハッシュだけを保存 |
| email_tokens | token_hash, purpose(verify/reset), email, user_name, expires_at | 1回限り有効 |
| exams | id, user_id, name, sort_order, exam_date, daily_goal | ユーザー内で名前が一意。exam_date（YYYY-MM-DD）と daily_goal（1〜1000）は任意（v2 で追加） |
| categories | id, exam_id, name, sort_order | 試験内で名前が一意（大文字小文字を区別しない） |
| practices | id, user_id, exam_id, title, created_at, completed_at | 未完了はユーザーごとに最大1件（部分ユニークインデックス） |
| answers | id, practice_id, title, question_number, area, response, elapsed_seconds, answered_at, correct, correct_answer, note | UNIQUE(practice_id, title, question_number) |

回答とカテゴリは、元の仕様どおり ID ではなく**カテゴリ名**で結び付く。

## 7. セキュリティ

元の資料では再設計の対象とされていたため、次のとおり設計した。

- パスワード：Argon2id でハッシュ化。8〜128文字
- セッション：ランダムな 256 ビットのトークンを HttpOnly / SameSite=Strict の Cookie で渡す。有効期間は既定7日
- CSRF 対策：状態を変える要求には `X-Requested-With` ヘッダーを必須にし、ログイン後は `X-CSRF-Token` がセッションの値と一致することを確認する
- 通信の暗号化：インターネット公開時は HTTPS のみ（http は https へ転送、HSTS 1 年、TLS 1.2 / 1.3 だけを許可）。設定は `deploy/nginx/study-record-https.conf`
- nginx での回数制限：ログイン・登録系 API は接続元 IP ごとに 1 分 10 回、API 全体は 1 秒 20 回まで（超えると 429 をアプリと同じ JSON 形式で返す）
- ログイン試行の制限：メールアドレスごと・接続元 IP ごとに、15分以内に5回失敗したら15分ロック（設定で変更可）
- メール送信の連打対策：同じアドレスへは1分に1回まで
- 登録状況を推測されない：新規登録・再送・再設定の応答は、登録の有無によらず同じにする
- パスワード再設定後はすべての端末をログアウト、パスワード変更後は今の端末以外をログアウト
- 認証情報（SMTP のパスワードなど）はソースコードに書かず、`config/app.ini` か環境変数で渡す（`app.ini` は Git に登録しない）
- CSV の書き出しでは、`=` などで始まる値の先頭に `'` を付け、表計算ソフトで数式として解釈されないようにする

## 8. ログ

- 出力先：`logs/SystemRunningLog.log`（標準出力にも同じ内容を出す）
- ローテーション：約2MB で `SystemRunningLog1.log` に切り替え、1世代だけ残す（`[log] max_bytes` / `backups` で変更可）
- 記録する内容：起動・停止、DB のマイグレーション、起動時の復旧の件数、すべての HTTP 要求（メソッド・パス・ステータス・処理時間）、ログインの成功・失敗・ロック、メール送信の成功・失敗、データの登録・変更・削除、入力の解析エラー、内部エラーの詳細
- 個人情報への配慮：メールアドレスは一部を伏せて記録する（例：`ta***@example.com`）。パスワード・トークンは記録しない
- ログ出力の初期化に失敗した場合は、実行フォルダの `SystemRunningLog.log` に直接書き込んでから終了する
